eLearning Platform

Full-Stack Learning Platform & Backend Engineering

I revisited a substantial university Django application and developed it into a coherent, production-oriented portfolio system: role-aware learning workflows, a scoped REST API, persistent PostgreSQL deployment, authenticated real-time discussion, explicit failure behaviour, and automated verification.

What the platform does

Learners can discover and enroll in courses, access enrollment-protected resources, leave feedback, receive notifications and join course-scoped discussion. Instructors can create and edit their own courses, manage learners and resources, and see activity connected to the courses they own. Anonymous visitors can browse the catalog without seeing protected resources or learner identities.

The application combines server-rendered Django workflows with Django REST Framework endpoints. I kept it as a Django monolith and retained templates: the domain and operational scope do not justify microservices or a separate SPA.

Role-aware experience

Learner and instructor dashboards prioritise genuine next actions and actual system state. The interface does not invent progress percentages because the data model has no completion events.

Scoped REST API

Public course reads sit alongside authenticated, role- and ownership-bound writes. Profile serializers minimise personal-field exposure and list endpoints are paginated.

Real-time discussion

Authenticated Django Channels consumers authorize course access, validate messages, persist them, and broadcast updates over WebSockets.

Explicit health signals

Liveness confirms the process answers HTTP; readiness and health execute a database query.

Authorization as a system boundary

The main hardening work was to make permissions consistent across every way into the system—not only the HTML views. Course creation, edits, resources and learner management require an instructor profile and ownership. Enrollment and feedback require the learner role, with active enrollment required for feedback. Resource downloads and WebSocket connections re-check course access rather than trusting the surrounding page.

Notification queries are scoped to their recipient; profile writes are owner-scoped; logout and notification-state changes use POST with CSRF protection. Database constraints reinforce rules such as one enrollment per learner/course and bounded feedback ratings.

Deployment architecture

The same codebase has deliberately different infrastructure profiles. Core learning actions continue to work when optional services are absent; the portfolio does not imply that the public free tier runs components it does not.

Public demo

Render + Neon

Daphne serves Django over ASGI; persistent Neon PostgreSQL stores application data; Channels uses a single-process fallback. Redis, Celery and background email delivery are not running.

Complete local stack

Docker Compose

Django / Daphne, PostgreSQL 16, Redis 7 and a Celery worker. Redis supports caching, the distributed Channels layer, and the Celery broker/result backend; PostgreSQL and uploaded media use named volumes.

Background work

Optional by design

Celery email tasks dispatch after the database transaction commits. If Celery is disabled or unavailable, the successful enrollment or feedback write is preserved and the optional failure is logged.

Testing & CI

All 85 tests pass. The suite covers models and database constraints, forms and authentication, HTML workflows, scoped REST endpoints, role and ownership permissions, optional-service failure, external-service fallbacks, Celery task behaviour, Redis/cache degradation, and end-to-end ASGI WebSocket authorization, persistence and broadcast.

The passing GitHub Actions workflow starts PostgreSQL 16 and Redis 7 services, checks for migration drift, applies migrations to PostgreSQL, runs Django system checks, verifies the production static build, and executes the complete test suite.

Known limitations

This is a demonstration-ready learning platform, not an enterprise LMS or a production-proven service. It models courses and resources, but not modules, lessons, assignments or completion progress. The interface received accessibility-conscious improvements, not a formal accessibility audit or user study.

The free public service can cold-start. Uploads are disabled because no persistent object storage is provisioned; Redis/Celery background processing and email are disabled; and the in-memory Channels layer only supports the service's single process. The complete Docker stack demonstrates the distributed Redis/Celery architecture locally.

What I learned

Productionising an existing system is largely about defining and testing boundaries.

Which data is public? Which action requires which role? What must commit before background work begins? Which dependency is optional? What does a health endpoint actually prove? Which product claims does the underlying data support? Answering those questions made the application more coherent than simply adding more technology would have.
