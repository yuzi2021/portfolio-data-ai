SkillPath Navigator

A validated data pipeline and REST API over a job–skill dataset

SkillPath loads 464 job postings, 319 skills and 5,845 job–skill relationships into a relational database and answers questions about them through a Django REST Framework API: skill demand, skills by role, job matching by skill set, and skill co-occurrence.

After the original coursework API, I added an ETL command that validates every row and cross-file reference before an atomic, repeatable load; PostgreSQL support alongside SQLite; Docker Compose; analytical SQL; a GitHub Actions workflow that runs all 44 tests against PostgreSQL 16; a browser interface over the API; and a public deployment on Render.

Phishing Detection: signal or artifact?

What a high score does and does not tell you about a model

The question was whether a neural-network classifier recognises phishing from genuine cues, or from properties of the datasets it was trained on. The assignment limited models to TensorFlow Dense and Dropout layers.

Preparing the data

Phishing examples came from the Nazario corpus (mbox files) and legitimate ones from Enron (a maildir of individual files), so each needed its own loader into a shared record of source, label, headers and body. HTML bodies were converted to text, attachments ignored, binary payloads decoded defensively and oversized messages capped. I deduplicated before splitting so identical emails could not appear in both training and test data, balanced the classes to 4,544 each, and made stratified splits of 6,361 / 1,363 / 1,364. The vocabulary was fitted on the training set only.

Training and evaluation

I compared a single-unit baseline (equivalent to logistic regression) with larger networks, dropout and smaller models, repeating each configuration across three random seeds. Two input variants — with and without email headers — used identical splits. The test set was used once, for the selected model:

Headers included

F1 0.998 · precision 1.000 · recall 0.996

Body only

F1 0.970 · precision 0.967 · recall 0.974

Unexpected behaviour, explainability and generalisation

The single linear unit already scored almost as well as the deeper models, and regularisation made no meaningful difference — signs of an easily separable task. SHAP attribution showed that 18 of the 25 most influential tokens in the headers model were mail-routing and source artifacts rather than phishing cues. The body-only model leaned more on recognisable cues such as credential language, generic greetings and brand names, but every phishing email still came from one corpus and every legitimate one from another. Applied unchanged to 8,000 emails from five other benchmark collections, its recall fell from 0.97 to 0.38 while precision stayed at 0.90. Those collections also label ordinary spam as positive, so this is a boundary check rather than a clean test — but it shows the within-corpus score does not transfer unchanged.

What I took from it

How the data was assembled mattered more than the model architecture. A clean train/test protocol only proves a model generalises within the same distribution; if a shortcut exists in the data, the test set shares it. I now look at where each class came from before trusting a metric.

GRC Change Monitor

Self-directed · source private

A weekday GitHub Actions pipeline that checks six official security and data-protection sources through RSS, JSON and HTML adapters, normalises each item, fingerprints its metadata to detect new and updated items, and stores changes, history and source health in SQLite. A failed or partial source run is never reported as “no changes”, and first-run items are recorded as a baseline rather than as new events. 67 deterministic tests use recorded responses and run before each monitoring run. SMS spam classification

CM3015 coursework
