SkillPath Navigator

A validated data pipeline, relational database and REST API over a job–skill dataset

Stack
Python · Django · Django REST Framework · PostgreSQL 16 · SQLite · SQL · GitHub Actions · Docker Compose · Gunicorn · Render
Context
Began as University of London web development coursework; the data pipeline, PostgreSQL support, containers, CI, interface and deployment were added independently
Access
Public demo live · source repository private

SkillPath loads a fixed snapshot of entry-level job postings and the skills they require into a relational database, then answers questions about it through a REST API: which skills are most in demand, which skills go with a given role, which jobs best match a set of skills, and which skills tend to appear together.

It is the project where I have worked across the most layers at once — data files, loading logic, database, API, browser interface, tests, CI and deployment — and had to work out which layer a problem was really in.

The engineering problem

The analyses are only as trustworthy as the data under them.

The dataset arrives as three CSV files — jobs, skills and the links between them — that must agree with each other. A job–skill link that points to a job that does not exist, a date in the wrong format, or two different rows claiming the same key would quietly distort every count the API returns.

So the loading had to be strict, explain what it rejected, be safe to run more than once, and never leave the database half-written. And the whole system had to behave the same way on SQLite locally, PostgreSQL in CI, and the deployed demo.

Architecture & data flow

Data moves in one direction, from the CSV snapshot to the browser. Each layer has one job.

1 · Source data

Three CSV files: job postings (dated 12–17 January 2024), skills with categories, and job–skill links.

2 · ETL command

A Django management command that runs extract → validate → transform → load, with a validate-only mode that checks the files without touching the database.

3 · Database

Jobs and skills in a many-to-many relationship through an explicit join table; bookmarks with notes and an application status reference jobs. SQLite by default, PostgreSQL when configured.

4 · REST API

Django REST Framework endpoints for skill demand, skills by role, job matching, skill co-occurrence and bookmark create/read/update/delete, documented with Swagger and ReDoc.

5 · Web interface

A Django template with plain JavaScript that calls the same public API, so the interface exercises the API rather than bypassing it.

6 · Delivery

GitHub Actions for checks and tests; Render rebuilds the demo from the checked-in CSVs, and deploys only after the checks pass.

Implementation decisions

Reject the whole snapshot

Validation checks file presence and headers, required fields and field lengths, URL syntax, date format and range, allowed categories, duplicate keys, and that every link points to a job and a skill in the same snapshot. One malformed row or conflicting duplicate rejects everything, with the reason and line number.

Distinguish skip from reject

An exact duplicate row is harmless and is skipped and counted. A duplicate key with different content is a genuine conflict and is rejected. Each run reports processed, loaded, skipped and rejected counts for every file.

Make loading safe to repeat

The load runs inside a single database transaction and skips keys that already exist, so running it twice changes nothing. The optional clear-and-reload validates first, so bad data can never delete good data.

Configure through the environment

The same code runs on SQLite, local PostgreSQL, Docker Compose and the hosted demo, selected by environment variables. With debug off, the application refuses to start unless a secret key is set.

I also wrote four analytical SQL queries against the real tables — top skills, category frequencies, jobs by number of skills, and postings by country and work type — each with its equivalent Django ORM expression, to check that I understood what the ORM was generating.

Testing & reliability

The suite has 44 tests: 29 from the original coursework covering the API, 11 for the data pipeline, and 4 for the interface. The pipeline tests feed the loader deliberately broken files — an invalid or future date, a missing field, a bad URL, a conflicting duplicate, an unknown skill reference, a wrong header — and check that each is rejected without writing anything.

On every push, GitHub Actions runs the following against a real PostgreSQL 16 service:

  • Confirm the connection really is PostgreSQL, and fail rather than fall back to SQLite
  • Run Django’s system checks and confirm no model change is missing a migration
  • Apply the migrations
  • Validate the checked-in dataset without loading it
  • Run the full test suite

Some problems only appear under production settings, where debug is off, HTTPS is enforced and static files are served differently. One interface test therefore loads the page under exactly those settings, and another checks that its CSS and JavaScript can actually be found.

Known limitations

The dataset is a historical January 2024 snapshot and does not update. Its original collection scripts are not part of the project, so its provenance cannot be reproduced. The API allows anonymous access and bookmarks are shared rather than owned by a user. The public demo uses SQLite on temporary storage, rebuilt from the CSVs on each deploy — fine for a demonstration, not for keeping user data.

What I learned

Most of the engineering is in deciding what should happen when things go wrong.

Writing the happy path took far less time than deciding what counts as a bad row, what the loader should say about it, and what state the database is left in afterwards. Testing against PostgreSQL rather than only SQLite, and under production settings rather than only debug mode, means the tests cover the configurations the system actually runs in, not just the convenient one.

When something failed, the useful question was which layer it lived in — the data, the loader, the database, the API or the browser — and reproducing it there before changing anything. That habit is what I most want to keep developing on larger systems.
